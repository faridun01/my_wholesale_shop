## Окончательные правила

Последнее прямое уточнение пользователя имеет приоритет над прежним требованием
автоматически возвращать оплату:

| Операция | Текущая накладная | Внесено | Долг |
|---|---:|---:|---:|
| Продажа | 1000 | 0 | 1000 |
| Три платежа по 200 | 1000 | 600 | 400 |
| Возврат товара на 150 | 850 | 600 | 250 |
| Ещё возврат на 350 | 500 | 600 | 0 |

Возврат товара не меняет платежи, не создаёт автоматическую выдачу денег,
кредит клиента или переносимый остаток. Исторические 600 остаются видимыми.
Деньги, физически возвращённые продавцом вне приложения, невозможно сверить
с кассой по данным приложения. Сторно ошибочного платежа — отдельное событие,
сохраняющее исходную запись.

Налогов нет. Ненулевой налог отклоняется до округления, включая 0.004.
Исторические налоговые столбцы сохранены и не участвуют в новых расчётах.
Возврат расхода сохраняет существующее отдельное правило: сначала уменьшение
долга расхода, затем возврат оплаченной части по исходным способам оплаты.

## Расчёт и движение данных

1. Формы продажи, прихода, оплаты и возврата передают деньги и ставки через общий
   JSON-преобразователь десятичными строками. ID и количества остаются числами.
2. Backend проверяет деньги, скидки, целые количества продажи/возврата,
   отсутствие налога, доступ к складу и ключ повторного запроса.
3. `InvoiceService.createInvoice` рассчитывает строки и распределяет скидку.
   Накладная, FIFO-списание, исходный снимок и первоначальная оплата сохраняются
   в одной транзакции.
4. При оплате блокируется накладная и проверяется долг. Повтор с тем же ключом
   не создаёт второй платёж; другое тело с тем же ключом отклоняется.
5. `InvoiceService.returnItems` использует исходные цены, количества и
   распределённую скидку. Возврат, его товарные строки, восстановление партий
   и новый итог накладной записываются атомарно. Платежи не уменьшаются.
6. API деталей отдаёт текущую накладную, первоначальный снимок, изменения,
   платежи и возвраты. Печать текущей накладной использует текущий итог;
   документ возврата — стоимость именно этого события.
7. Отчёты используют чистую выручку строк и оставшиеся FIFO-затраты. Выручка
   отличается от полученных денег. Валовая прибыль — выручка минус себестоимость
   оставшихся продаж; расходы и списания учитываются соответствующими отчётами.

### Формулы

Для цены P, количества Q и скидки товара d сохранено существующее правило:
`U = ceil_cent(P × (1 − d/100))`, `L = U × Q`.
Округление цены после скидки вверх до копейки не заменялось другим правилом.

Скидка накладной D округляется HALF_UP до 0.01. В копейках она распределяется
пропорционально L методом наибольших остатков со стабильным порядком при равенстве.
Сумма распределений равна D. Общая функция поддерживает фиксированную скидку;
это не вводит новый тип скидки в интерфейсы, где предусмотрен только процент.

`E_i = L_i − allocated_discount_i` — исходная возвращаемая стоимость строки.
Для уже возвращённых q единиц и нового возврата k:

`refund_i = round_cent(E_i × (q+k)/Q_i) − round_cent(E_i × q/Q_i)`.

Стоимость 0.13 за три единицы возвращается как 0.04, 0.05, 0.04. Полный возврат
равен исходным 0.13, без потери копейки на последовательных операциях.

`current_net = original_net − cumulative_returns`.
`debt = max(0, current_net − applicable_payments)`.

### Decimal

Канонический модуль — `backend/src/utils/financial.ts`; frontend-копия
`frontend/src/utils/financial.ts` генерируется `scripts/sync-financial.mjs`.
Тождество проверяет тест. Используется decimal.js-light 2.5.1, precision 80,
явные режимы округления. Финансовые сложения, умножения, скидки, распределения,
себестоимость и агрегаты переведены на Decimal.

Основные суммы БД — Decimal(12,2), стоимость складского события — Decimal(18,2),
финансовые ставки — Decimal(65,30). В SQL количества приводятся к numeric перед
умножением на цену, чтобы выражение не становилось double precision.

Не каждый объект JavaScript стал Decimal: совместимые методы могут вернуть
number после округления и проверки диапазона; графики и отображение используют
числа на границе представления. API-типы допускают строки и прежние числа.
Входная десятичная строка сохраняет точность; точность, потерянную внешним
клиентом до отправки number, сервер восстановить не может. ID и счётчики — не деньги.

## Рабочая база: только чтение

Источник — локальная `my_wholesale_shop`. Скрипт
`backend/scripts/audit-financial-readonly.ts` использует транзакцию READ ONLY.

По выполненным SQL-проверкам: 0 расхождений платежей с оплаченной суммой накладной,
возвратов с накопленной суммой возврата, строк с суммой накладной, скидки/возврата
с чистым итогом. Также 0 превышений возвратов, потерянных связей, неверных скидок,
ненулевых налогов, проверяемых отрицательных сумм, расхождений оплат расходов
и количеств FIFO-распределений.

Это проверка согласованности сохранённых значений, не доказательство достоверности
всех первоначальных цен или физически переданных наличных.

| Историческая проблема | Наблюдение | Что требуется |
|---|---|---|
| Товар 70 | stock = 100, сумма оставшихся партий = 0 | Сверка документов и склада, отдельная согласованная корректировка |
| Товар 64 | stock = 16, сумма оставшихся партий = 0 | Та же сверка; не создавать фиктивный приход |
| Возврат 11 / накладная 57 | 14, нет точной товарной детализации | Сохранить сумму, неизвестные детали не выдумывать |
| Возврат 12 / накладная 57 | 98, то же | Восстановление только по первичным документам |
| Возврат 13 / накладная 57 | 52.56, то же | То же |
| Возврат 14 / накладная 81 | 661.78, то же | То же |
| Запрошенный №115 | Нет возврата ID 115 и возврата по накладной 115 | Нужен другой источник/номер документа, если он существует |

Причина именно двух старых расхождений stock не доказана. Чтение исправлено
на партии, но историческая база не переписана. В рабочей схеме пока отсутствует
`return_items`. Найденные 27 складских событий типа return включают разные
процессы и не доказывают состав четырёх возвратов. Подбор по времени не использован.

## Миграции и воспроизведение

Все 25 миграций успешно применены к новым изолированным локальным БД. Runner
разрешает только локальный сервер и имя с суффиксом `_financial_test`; удаляет
только созданную им БД. Prisma защищён от случайного подключения основной БД
в режиме финансовых интеграционных тестов.

Новые миграции этапа:

- `backend/prisma/migrations/20261109000200_decimal_financial_rates/migration.sql`
  — ставки Float → Decimal(65,30), без удаления записей.
- `backend/prisma/migrations/20261109000300_exact_inventory_cost/migration.sql`
  — точная стоимость и состав партий складского события.
- `backend/prisma/migrations/20261109000400_inventory_operation_keys/migration.sql`
  — уникальные ключи и хеши складских операций.

В рабочей базе миграции **не применялись**. Проверка пустой изолированной БД
не заменяет проверку обновления копии существующих данных. Смена Float на Decimal
не восстанавливает точность, утраченную до сохранения исторических значений.

```powershell
node backend/scripts/test-financial-postgres.mjs --reporter=default --reporter=json --outputFile=../docs/financial-test-results.json
npm.cmd --prefix backend run build
npm.cmd --prefix frontend run build
node backend/node_modules/prisma/build/index.js validate --schema backend/prisma/schema.prisma
node --import ./backend/node_modules/tsx/dist/loader.mjs backend/scripts/audit-financial-readonly.ts
git diff --check
```

Backend build/typecheck, frontend build/typecheck, Prisma validation и diff-check
успешны. Frontend-сборке потребовался запуск вне ограничений песочницы из-за
доступа esbuild к родительским каталогам. Развёртывание, Docker build и полный
браузерный E2E в этом проходе не выполнялись; их успешность не заявляется.

Перед рабочим использованием нужны проверка миграций на копии текущей базы,
согласованное развёртывание и браузерная проверка продажи, оплаты, возврата и печати.
Два старых остатка и детализация возвратов требуют первичных документов и отдельно
согласованной корректировки. Автоматического изменения истории не было.
