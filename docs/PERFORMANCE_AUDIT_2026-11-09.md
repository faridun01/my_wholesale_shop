  с отдельным импортом типа. Это исправление запуска, не оптимизация арифметики.

## Как ускорять дальше — порядок работ

1. **Товары и клиенты: только при измеренной необходимости.** Продажи переведены
   на серверные страницы (см. раздел ниже). Товары и клиенты загружаются полностью,
   постранично: группировка по имени, поиск дублей, слияние, PDF, итоги долгов и
   сегменты работают на полном списке, а их перенос в SQL дублировал бы финансовую
   логику. Менять это стоит, когда замеры на реальном объёме покажут медленную
   загрузку; начинать тогда с облегчения ответа, а не с переноса расчётов.
2. **Отчёты за большие периоды.** `/reports/analytics`, `/sales`, `/profit`
   читают строки периода в память. Следующий этап — SQL-агрегации там, где они
   сохраняют точные скидки/FIFO, отдельная пагинация детализации и выгрузка.
   Проверять совпадение с финансовым эталоном; не ограничивать итог первыми N строками.
3. **Dashboard.** `/dashboard/summary` запускает около 20 верхнеуровневых операций
   и загружает части данных для агрегации в Node. Проверить каждую по EXPLAIN на
   репрезентативной копии; объединять подходящие агрегации. Promise.all не отменяет
   очередь соединений пула. Число соединений подбирать по измерениям, не увеличивать
   вслепую и не добавлять PgBouncer без необходимости.
4. **Быстрые изменения фильтров.** ReportsView защищён от перезаписи свежих данных
   старым ответом, но предыдущий HTTP-запрос не отменяет. AbortController и debounce
   могут убрать ненужные запросы при быстрой смене фильтров. Отмена браузерного
   запроса сама по себе не гарантирует отмену уже запущенного SQL.
5. **Нагрузка и сеть.** На отдельной копии с реалистичным объёмом собрать p50/p95,
   число SQL-запросов, размер ответов, CPU/RAM, ожидание блокировок и пула при
   нескольких уровнях конкуренции. В браузере измерить загрузку продаж, POS и
   отчётов с ограничением скорости сети. После этого выбирать следующие изменения.

Кэшировать долги, оплаты и остатки без корректной инвалидизации нельзя.
Историю и финансовые проверки ради скорости удалять нельзя. Redis, новые
индексы, замена сервера и увеличение пула пока не обоснованы измерениями.

## Серверный список продаж

Экран продаж запрашивает только текущую страницу (8 накладных) вместо 500. Поиск,
статус, сотрудник, даты и сортировка выполняются в SQL, поэтому поиск больше не
ограничен первыми 500 накладными. Формат строки ответа `/invoices` не изменён;
вызовы со старыми параметрами (карточка сотрудника) работают как раньше.

- Статус и сортировка по оплате/долгу считаются в SQL по тем же правилам, что
  значок в таблице, а не по сохранённому полю `status`.
- Границы дат браузер передаёт точными моментами (`from`/`to`): сервер может
  работать в UTC, а день пользователя — местный.
- Поиск с запросом выполняется с ILIKE без индекса. Индекс не добавлялся: при
  текущем объёме оснований нет, решать по EXPLAIN на реальном объёме.
- Сортировка по имени: без учёта регистра, порядок задаёт collation БД; он может
  немного отличаться от прежнего `localeCompare` браузера (например, для «ё»).

Проверено 12 интеграционными тестами с PostgreSQL через настоящие HTTP-маршруты
(`backend/src/routes/invoices.list.postgres.test.ts`). Браузерная проверка экрана
не проводилась.

## Полные списки товаров и клиентов

Запрос к `/products` и `/customers` молча обрывался на 500 записях: дальше товары и
клиенты пропадали из кассы, выгрузок и итогов долгов. Теперь `fetchAllPages`
загружает все страницы, а сервер отдаёт их в стабильном порядке (у `/products`
порядка не было, страницы могли повторять и терять записи). Проверено в
`backend/src/routes/list-paging.postgres.test.ts`. При большом объёме экран
загружает больше данных, чем раньше: это цена полноты списка.

## Часовой пояс сервера

В `docker-compose.yml` для бэкенда задан `TZ=Asia/Dushanbe`: периоды отчётов и окна
dashboard строятся по календарному дню сервера, и в UTC продажи с полуночи до 05:00
попадали в предыдущий день. Подписи дат в отчётах продаж, прибыли, возвратов и
списаний переведены на тот же день (`toLocalDateKey`), иначе они расходились бы с
периодом. Сохранённые данные не меняются, меняется только разбивка по дням.
